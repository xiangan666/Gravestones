# GitHub 发布流程

## 首次准备

1. 核实 `NOTICE.md` 中原始素材授权，再决定仓库可见性与许可证。
2. 在GitHub创建目标仓库，将当前源码提交上传。仓库地址由维护者自行确定，文档不虚构GitHub账号或地址。
3. `dist/` 和 `node_modules/` 已忽略；原始归档用于溯源，公开分发前同样核实权限。

## 校验与构建

```powershell
npm ci
npm run check
npm test
npm run build
Get-FileHash -Algorithm SHA256 dist/Gravestones-lanshiyi-v2.0.13.mcaddon
```

每个版本生成一个合并行为包与资源包的 `.mcaddon` 安装包，直接导入即可。**从2.0.11开始，新版本构建不删除旧版安装包、已有校验文件或其他资料**；同版本重新构建只覆盖同名安装包。SHA-256值在日志中显示，不另生成校验文件。原始2.0.8归档不受影响；曾被旧构建脚本删除的版本不会自动恢复。

归档只收录 `Grave_B/` 和 `Grave_R/`，不会打入node_modules、原生测试服务端/世界、测试、原包、个人路径或文档。固定zip时间戳和排序保证相同输入产生相同SHA-256。

GitHub的 `validate.yml` 在push/PR时执行同样校验，并上传构建产物。`release.yml` 在推送 `v2.0.13` 之类版本标签时，要求标签与package.json版本相同，只上传与标签对应的安装包，校验构建后生成**草稿Release**；不会把保留的其他历史包混进新Release。维护者仍需审核发布说明及真实游戏验收后手动发布。

## 版本约定

功能更新和问题修正统一递增版本号，每个版本交付一个标准命名的安装包：`Gravestones-lanshiyi-v<版本>.mcaddon`。版本从原版展示版本2.0.8，经2.0.9、2.0.10、2.0.11、2.0.12升至当前2.0.13。行为包/资源包header、各module以及互相依赖版本保持 `[2, 0, 13]`；npm项目、版本常量、包文件名和更新日志一致。稳定Script API依赖版本仍为2.0.0，不随模组版本机械修改，不要求Beta API。

`prepare_assets.py` 从package.json读取版本并生成包名及版本，避免再次执行生成器时回写旧版号。生成后仍需同步版本常量和相关文档并运行检查。

## 发布前清单

- [ ] 原素材授权和归属已确认。
- [ ] 自动化检查全部通过。
- [ ] `docs/TESTING.md` 中真实客户端/BDS验收已记录。
- [ ] 原世界升级已在副本验证，已备份用户存档。
- [ ] 包UUID保持不变，所有展示版本与依赖一致。
- [ ] Release说明明确最低引擎、命令权限、keepInventory、菜单合成和旧版经验限制。
- [ ] 上传单个安装包，附上更新日志及联系邮箱；需要时将构建日志中的SHA-256值写入发布说明。

本次交付仅编写文档、源码和工作流，没有执行git远程操作、上传或线上发布。
